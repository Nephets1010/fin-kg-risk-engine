## 二、RedisJobStore（`src/fin_kg/api/jobs.py`）

### [B-01] `RedisJobStore` **从未被接入**：生产多 worker 部署下 job 状态跨进程不可见

- **文件**: `src/fin_kg/api/deps.py:170-173`、`src/fin_kg/api/jobs.py:160`
- **问题**:
  `get_job_store()` 无条件返回内存版 `JobStore()`：
  ```python
  @lru_cache(maxsize=1)
  def get_job_store() -> JobStore:
      """Return the job registry."""
      return JobStore()
  ```
  `RedisJobStore` 在整个 `src/` 中**没有任何构造点**（只有 `api/__init__.py` 的 re-export）。
  而 `Settings.workers` 默认 **4**（`config/settings.py:149`），
  `Dockerfile:64` 的 CMD 是 `uvicorn ... --workers 4` —— **4 个独立进程各持一份内存 job 注册表**。
  `POST /api/v1/jobs/ingest` 落进程 A，随后的 `GET /api/v1/jobs/<built-in function id>` 有 3/4 概率
  落到另一个进程 → `NotFoundError` → **404**。
  `jobs.py:11-13` 的 docstring 明确宣称 Redis 版就是为多 worker 部署准备的 ——
  该能力**写了但没接线**，与前五轮已修的「API Key 鉴权未挂载」属同类缺陷。
- **影响范围**: 「Init → Step → Poll」长任务契约在**任何多 worker 部署下失效**。
  官方 `docker-compose.yml` / `docs/deployment.md` 推荐的正是 4 workers。
- **风险等级**: **高**
- **是否可立即修复**: **是**（但须先修 B-02 ~ B-07）—— 决策依据见**第十一节**。

### [B-02] `RedisJobStore.update()` 不回源 Redis，多 worker 场景下更新他人创建的 job 直接 `NotFoundError`

- **文件**: `src/fin_kg/api/jobs.py:199-202`（对照 `:180-197` 的 `get`）
- **问题**:
  `get()` 有 Redis → 本地内存的两级回退；`update()` **没有**：
  ```python
  def update(self, job_id: str, **changes: Any) -> Job:
      job = super().update(job_id, **changes)   # 只查 self._jobs (本进程内存)
      self._write(job)
      return job
  ```
  `super().update()` 在 `self._jobs` 里找不到就 `raise NotFoundError`。
  worker B 想更新 worker A 创建的 job → **即使 Redis 里明明存着这个 job**，也直接抛
  `NotFoundError`。这正是 `run_async` 的后台线程路径。
- **验证**:
  ```
    F. 多 worker 竞态：worker B 更新 worker A 创建的 job
  ```
- **影响范围**: RedisJobStore 的核心卖点（多 worker 共享 job 状态）在**写路径**上不成立，
  只有读路径成立。属于「看起来能用、实际一半能用」的陷阱。
- **风险等级**: **高**
- **是否可立即修复**: **是** —— `update()` 改为：先查本地 → 再查 Redis → 都没有才 `NotFoundError`；
  并把 Redis 里的对象回填进 `self._jobs` 后再改。

### [B-03] `RedisJobStore` 写 Redis **不带 TTL**，且 `max_jobs` 淘汰只作用于内存，Redis 键**永不过期**

- **文件**: `src/fin_kg/api/jobs.py:204-218`（`_write`）、`:86-107`（`_evict_locked`）
- **问题**:
  ```python
  self._redis.set(self._key(job.id), json.dumps(payload, ensure_ascii=False))
  ```
  没有 `ex=` 参数。内存版 `JobStore` 有完整的两级上限（`max_jobs=500` + `ttl_seconds=86400`，
  见 `jobs.py:80-107`），但这两个机制**只作用于 `self._jobs`**，
  `_evict_locked` 从不删除 Redis 键 → Redis 中的 job 键**只增不减、永久保留**。
- **验证**:
  ```
    E. TTL / 过期键清理
  ```
- **影响范围**: Redis 内存随接入请求数**线性无界增长**，且每个键含完整 result payload
  （摄入报告可能很大）。长跑实例最终 OOM —— 一类典型的「静默资源泄漏」。
- **风险等级**: **高**
- **是否可立即修复**: **是** —— `_write` 改为 `set(key, payload, ex=self._ttl_seconds)`，
  并在 `_evict_locked` 中同步 `delete` 对应 Redis 键。需把 `max_jobs/ttl_seconds` 透传给
  `RedisJobStore.__init__`（当前签名 `jobs.py:167` 不接受这两个参数）。

### [B-04] `RedisJobStore` 的读-改-写是**整文档覆盖写**，并发更新会丢字段

- **文件**: `src/fin_kg/api/jobs.py:199-218`
- **问题**:
  `_write()` 把整个 `Job` 序列化后 `SET` 覆盖，没有 `WATCH/MULTI`、没有版本号、
  没有字段级合并。两个线程各改不同字段时，后写者用自己**过期的整份快照**覆盖前写者。
- **验证**:
  ```
    G. 并发 update 的丢更新（read-modify-write 竞态）
  ```
  （该用例用一次性 hook 精确控制交错时序，避免依赖调度运气。）
- **影响范围**: job 的 `progress` / `result` / `error` 等字段在并发写入下可能相互覆盖。
  当前 `run_async` 是单线程写，尚不易触发；但 B-01 一旦接线（多 worker + 共享 Redis），
  立刻成为真实竞态。
- **风险等级**: **中**
- **是否可立即修复**: **否**（在 B-01 接线之前意义不大）—— 正确做法是用 Redis Hash 并对字段
  分别 `HSET`，或加版本号做乐观锁；这需要重新设计序列化格式，会影响 B-05 的字段比对结论。

### [B-05] `Job.as_dict()` 与 Redis 序列化 payload 的**字段名不一致**（4/9 个字段键名不同）

- **文件**: `src/fin_kg/api/jobs.py:49-60`（`as_dict`）、`:204-218`（`_write`）
- **问题**:
  `as_dict()` 是 **camelCase** 的 API 契约（`jobId`/`jobType`/`createdAt`/`updatedAt`），
  `_write()` 存的是 **snake_case** 的内部字段名（`id`/`job_type`/`created_at`/`updated_at`）。
  两者语义等价但键名不同，任何「直接读 Redis 键当 API 响应返回」的写法都会拿到错的字段名。
  逐字段比对见**附录 A**。
- **验证**: 见附录 A。补充确认：Redis 往返本身是**无损**的。
- **影响范围**: 当前无实际故障（`get()` 内部自洽），但它是一个**契约陷阱**：Redis 里的
  payload 是平台内部格式，不是 API 契约格式，任何按 API 文档解析 Redis 的第三方消费者都会失败。
- **风险等级**: **低**
- **是否可立即修复**: **是** —— 建议 Redis 侧也用 `as_dict()` 的 camelCase 键，
  或在 `docs/api.md` 明确「Redis 中的 job payload 使用 snake_case 内部格式」。

### [B-06] Redis 不可用时 `create()` **先写内存再写 Redis**，异常上抛但内存留下孤儿 job

- **文件**: `src/fin_kg/api/jobs.py:175-178`
- **问题**:
  ```python
  def create(self, job_type: str) -> Job:
      job = super().create(job_type)   # 已写入 self._jobs
      self._write(job)                # 此处抛异常
      return job
  ```
  Redis 挂掉时 `self._redis.set` 抛 `ConnectionError`，异常向上传播（**不是静默丢失**，
  这一点是好的），但 `self._jobs` 里已经留下了一个从未持久化的 job。
  另外 `get()` 的 `self._redis.get(...)` 同样直接上抛，**不回退到本地缓存**——
  即 Redis 一挂，整个 job 子系统完全不可用，本地缓存形同虚设。
- **验证**:
  ```
    D. Redis 不可用时的行为
  ```
- **影响范围**: Redis 抖动时 job 接口整体 500；残留的孤儿 job 会在内存里累积到
  `max_jobs` 才被淘汰。
- **风险等级**: **中**
- **是否可立即修复**: **是** —— `get()` 加 `try/except` 回退到 `super().get(job_id)`；
  `create()` 改为「先写 Redis 成功、再写内存」，或在异常时把内存里的 job 移除。

### [D-01] P-8 的溯源「读-改-写」丢更新**已用真实并发复现确认** —— 仍未修复

- **文件**: `src/fin_kg/ingestion/pipeline.py:294-339`（`_align_node` + `_merge_provenance`）
- **问题**:
  `_align_node` 的逻辑是：`existing = get_node(id)` → `_merge_provenance(node, existing)`
  → `upsert_nodes([node])`。这是典型的**非原子读-改-写**：
  读的是**旧快照**，合并后整份覆盖写回。Neo4j 的 `MERGE` 只保证节点/关系**不重复**，
  不保证**属性列表不丢**。
  两个 worker 同时向同一主体写入来自不同数据源的溯源时，各自读到相同的旧值，
  各自合并自己的一半，后写者用过期快照覆盖先写者 → **先写者的溯源永久丢失**。
- **验证**:
  ```
    B. 按 Neo4j 拷贝语义复现 P-8 溯源丢更新

    C. 顺序执行对照组 (同仓库, 无并发)
  ```
  复现脚本用 `threading.Barrier(2)` 保证两个 worker 都已读到旧快照后才继续，
  使竞态**必然**发生而非依赖调度运气。
- **影响范围**:
  溯源是本平台的**合规审计基础**（`docs/architecture.md` 溯源模型、`ADR-0003`）。
  丢失溯源意味着「这条数据是从哪来的」不可追溯 —— 在合规审计场景下这是严重问题。
  多 worker 接入（`docs/deployment.md` 的水平扩展方案）会稳定触发。
- **风险等级**: **高**
- **是否可立即修复**: **否**（需要设计决策）——
  正确解法是让合并在存储层原子化（Neo4j 侧用 `apoc.merge` 或把溯源拆成独立节点用
  `MERGE`+`SET` 追加），或引入乐观锁（版本号 + CAS 重试）。
  这是**架构级**改动，不能顺手改。台账 U-3 已按「确定性可复现，但修复涉及写入路径的可靠性取舍」
  记录为待确认项 —— **定性准确**。

### [D-08] `RiskService._persist_scores` 与并发 `rank()` 的互相覆盖（**影响有限**，已实测）

- **问题**:

  - **真正的风险在 B-01 接线之后**：多 worker 进程并发 `rank()` + 回写同一批节点，
    虽然值相同，但 `riskComputedAt` 时间戳会被无意义地互相覆盖。
- **风险等级**: **低**
- **是否可立即修复**: **否**（当前无实际故障）。

### [D-09] 存储抽象的语义一致性未被守护：文件图是**生产降级路径**

- **文件**: `src/fin_kg/graph/repository.py:245-246`、`:59-86`、`src/fin_kg/api/deps.py:81-89`
- **问题**:
  这是 D-02 的**跨清单升级**。单看 D-02 它像「测试盲区」，但把降级路径算进来就是**生产语义差异**：
  `create_repository()` 在 Neo4j 不可达且 `env != production` 时，会退到
  `FileGraphRepository`（`deps.py:85-89`），它继承 `InMemoryGraphRepository`。
  而这个内存实现的语义**比 Neo4j 宽松**：
  | 行为 | Neo4j | 内存图/文件图 |
  |---|---|---|
  | `get_node` 返回 | 全新记录（拷贝） | **活引用**（`repository.py:246`） |
  | 关系并发 upsert | 由数据库事务保证 | 靠 GIL 时序「恰好」幂等（D-06，无保证） |
  | 遍历时的并发写 | 快照隔离 | `RuntimeError: dictionary changed size during iteration`（D-03） |
  | 落盘 | 由 Neo4j 持久化 | 全量重写同一 `.tmp`（D-04 冲突） |
  也就是说：**同一份代码在「Neo4j 正常」与「降级到文件图」两种部署下行为不同**，
  而单测全部跑在内存图上（Neo4j 集成用例自动 skip），
  因此这个差异**没有任何测试能发现**。
- **验证**: 见 D-02 / D-03 / D-04 / D-06 四条的实跑输出。降级路径确认：
  ```
  $ grep -n "FileGraphRepository" -A 4 src/fin_kg/api/deps.py
      local = FileGraphRepository(
          resolved.resolve_path(Path("data/local-graph.json")), autosave=True
      )
  ```
- **影响范围**:
  降级是**运维事故时的兜底路径**，恰恰是最需要行为可预测的时候。
  D-01 的溯源丢更新在内存图上复现不出来，恰恰因为 `get_node` 返回活引用。
- **风险等级**: **中**
- **是否可立即修复**: **否**（需要设计决策）——
  最小修复是让 `InMemoryGraphRepository.get_node` 返回**拷贝**，与 Neo4j 对齐。
  但这只解决「返回值语义」一项；事务隔离、落盘原子性等仍需更大改造。
  **建议先在 ADR 里明确「内存图是 Neo4j 的近似，不保证并发语义」**，
  并把并发相关测试显式标注为「仅对 Neo4j 有效」，避免给出虚假的安全感。

### [E-01] `scripts/generate_sample_data.py` 的 `--seed` 是**空操作**，参数对输出零影响

- **文件**: `scripts/generate_sample_data.py:226-228`、`:523`、`:8-9`（docstring）
- **问题**:
  ```python
  def generate(output: Path, *, seed: int = 20260301) -> dict[str, int]:
      random.Random(seed)          # <-- 返回值被丢弃, 没有任何变量持有它
  ```
  `random.Random(seed)` 的结果**没有被赋值给任何变量**，后续代码也从未使用 `random` 模块
  （`rng`/`rand`/`shuffle`/`choice` 的出现次数为 0，`import random` 形同虚设）。
  因此 `--seed` 参数**完全不影响输出**。
  这本身不造成错误（输出确实可复现），但它让 `--seed` 成为**误导性的接口**：
  用户以为换 seed 会得到不同的数据集，实际得到完全相同的文件。
- **验证**:
  ```
    B. generate_sample_data.py --seed 的可复现性
  ```
- **影响范围**: 误导性接口。任何依赖 `--seed` 生成多样本数据集的测试或文档流程都会得到
  恒定输出，从而**产生虚假的通过**（例如「用不同 seed 验证去重逻辑」实际只测了一种输入）。
- **风险等级**: **中**
- **是否可立即修复**: **是** —— 二选一：
  (a) 若 seed 本就该有效：改为 `rng = random.Random(seed)` 并在生成事件/关系时使用 `rng`；
  (b) 若生成器本就不含随机性：**删除 `--seed` 参数与 `import random`**，
  并在 docstring 中说明「输出完全确定，无随机成分」。(b) 更诚实、成本更低。

### [E-03] `scripts/benchmark.py` 测的是**内存图**，其数字不代表生产；`--compare` 基线口径不一致

- **文件**: `scripts/benchmark.py:26`、`:83`、`:33-39`、`:149-171`
- **问题**（三个独立缺陷）：
  1. **测的不是生产 store**：`run_benchmark` 用 `InMemoryGraphRepository`（纯 Python dict），
     而生产是 Neo4j。脚本 docstring 第 3 行宣称「测量四个关键路径的耗时，**用于容量规划**」——
     用内存图的结果做容量规划会严重低估。
  2. **`--compare` 的基线口径不一致**：`BASELINE` 的 `companies = 10_000`，
     而 `compare()` 显式 `if key == "companies": continue` **跳过了规模这一维度**。
     于是用 `--companies 200` 跑出的 0.049s 会去和 10000 家公司的 12.0s 基线比，
     ratio = 0.004 → 判为 `improved`。**任何小规模运行都必然显示「improved」**，
     `--compare` 的结论不可信。
  3. **默认样本量不足以支撑 p95**：`Measurement.p95` 取
     `index = min(len(ordered) - 1, int(len(ordered) * 0.95))`。n=10 时 index = 9，
     即**取最大值**，p95 退化为 max；n=20 时 index=19，同样是 max。
     默认 `samples=50` 勉强可用，但 `--samples 10` 会得到无意义的 p95。
- **验证**:
  ```
    C. benchmark.py 的测量方法

    (段落未找到: -- --compare 的基线口径 --)
  ```
  另有一处**做对了**的地方：`propagate` 的 `risk_score` 在 `_time_call` **之外**计算
  （`benchmark.py:126-127`），评分时间未被计入传播耗时 —— 这一点是正确的，不列为缺陷。
- **影响范围**:
  1. 「容量规划」的唯一工具给出的是**内存图的数字**，与生产相差一个数量级以上；
  2. `--compare` 会**主动误导**：任何小于 10000 家公司的运行都报「improved」，
     真实回归会被完全掩盖 —— 这比没有基线更危险。
- **风险等级**: **中**
- **是否可立即修复**: **是** —— `compare()` 在 `companies` 不匹配时直接拒绝比较并报错；
  `BASELINE` 增加规模键；`p95` 改用 `statistics.quantiles` 或明确最小样本量门槛；
  脚本 docstring 明确标注「测的是内存图，仅供回归对比，不用于容量规划」。
